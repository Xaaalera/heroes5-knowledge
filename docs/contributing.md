# Предложить правку

Можно начать с опечатки, уточнения версии или небольшого примера. Для этого не нужно писать большое руководство.

## Сообщить о проблеме

[Создай issue на GitHub](https://github.com/Xaaalera/heroes5-knowledge/issues/new). Укажи страницу, спорное утверждение и то, что наблюдаешь в своей игре. Для технической ошибки добавь версию и шаги воспроизведения.

## Исправить статью

Кнопка «Исправить на GitHub» внизу статьи открывает её исходник. GitHub предложит создать ветку или fork и оформить pull request. Для этого нужен аккаунт GitHub.

Основные статьи лежат в `docs/`, английские версии — в `docs/en/`. При изменении факта обнови обе версии или явно отметь в PR, что перевод ещё нужен.

## Где живёт документация

Руководства, справочники и объяснения для наших модов, xkit и Game API публикуем на этом сайте. Их исходники должны храниться в репозитории базы знаний. README каждого проекта должен кратко объяснять назначение и вести на нужные страницы сайта. При переносе документации убираем её прежнюю живую копию; одну инструкцию не поддерживаем одновременно в нескольких репозиториях.

AGENTS.md хранит рабочие правила агента; лицензии остаются рядом с кодом. Датированные исследования и приватные журналы сохраняют историю проверки. Они не заменяют актуальную статью и не должны попадать на сайт вместе с личными путями, игровыми дистрибутивами или техническими адресами памяти.

## Написать статью для человека

Начни с задачи читателя: что он сможет сделать или понять. Выбери один основной формат — обучение на примере, инструкция к задаче, справочник или объяснение. Не прерывай первые шаги журналом разработки: для истории есть отдельный дневник.

- Назови, для кого статья и что потребуется до начала.
- Объясняй незнакомый термин при первом появлении. Пиши действия обычными словами.
- Давай команды, которые можно повторить; указывай, где их вводить и когда ждать завершения.
- Покажи ожидаемый результат и способ проверить его. Если возможен отказ, объясни следующий шаг.
- Отделяй реализованное от планов, наблюдение от предположения. Проверяй технические утверждения по коду и воспроизводимым результатам.
- Обновляй русскую и английскую версии вместе. Числа, ограничения и смысл действий должны совпадать.

Подход опирается на [Diátaxis](https://diataxis.fr/start-here/) и [правила пошаговых инструкций Google](https://developers.google.com/style/procedures). Тип страницы помогает выбрать форму текста; он не заменяет проверку фактов.

## Проверить статью пятью критиками

Каждая новая или изменённая статья проходит пять независимых проверок по [методу critique](https://github.com/Xaaalera/claude-skills/blob/main/plugins/critique/skills/critique/SKILL.md). Организуют их сопровождающие базы: автору правки достаточно отправить PR с источниками и описанием изменения. Для опечатки проверки могут быть короткими, но должны охватывать окончательный текст. Автор статьи не оценивает собственный текст как независимый критик.

| Зона | Что проверяет критик |
|---|---|
| Понятность новичку | Понятны ли цель, термины и первые действия без помощи автора или ИИ |
| Техническая точность | Подтверждены ли команды и ограничения кодом, источниками и наблюдениями |
| Воспроизводимость | Хватает ли подготовки, шагов и проверок результата для повторения |
| Структура и навигация | Легко ли найти нужный ответ, работают ли ссылки, нет ли лишних повторов |
| Терминология и перевод | Одинаковы ли названия, примеры, числа и смысл в RU/EN |

Критик указывает место, конкретную ошибку, её последствия, серьёзность и доказательство. «Мне не нравится стиль» без проблемы для читателя не считается дефектом. Проверяемые утверждения сверяем с источником или небольшим безопасным опытом.

Замечания собираем в один JSON: страница и хеш текста, критик и его зона, место ошибки, доказательство, серьёзность, решение и проверка исправления. Повторы объединяем по месту, не скрывая независимые совпадения. Текст не меняем посреди раунда; после правок проверяем исправленные места снова. Максимум — три раунда на статью. Подтверждённые существенные ошибки устраняем до публикации; спорные выводы честно помечаем непроверенными. Критика не заменяет сборку сайта, проверку ссылок и осмотр страницы.

## Подкрепить технический вывод

Отделяй наблюдения от предположений. Приводи версию игры, сценарий и небольшой пример. Не загружай дистрибутив игры, чужие закрытые материалы, токены и личные данные.

Скриншот должен показывать сам результат. Перед добавлением проверь, что на нём нет лишних окон и личной информации.

Для воспроизводимого опыта начни с [руководства xkit и тестовой копии](modding/devkit.md). [Статья о консоли](modding/console.md) объясняет ввод команды, подсказки, ответы и журнал.

## Устройство сайта

Markdown — единственный исходник статей. Оформление находится в `theme/` и `styles/`; готовый `site/` и скомпилированный CSS не редактируют и не коммитят. Сайт собирается независимо от приватной мастерской.

### Метаданные и статус статьи

В начале файла укажи `content_type`, `status`, `lang`, `translation` и `faction`. Типы: `tutorial` — учебный пример, `how-to` — задача с шагами, `reference` — справочник, `explanation` — объяснение; `landing` и `meta` используются для навигации и служебных страниц. Не добавляй пустые разделы ради шаблона.

`translation` — адрес парной статьи от корня сайта. У RU/EN должны совпадать тип, статус и фракция, а ссылки на перевод — вести друг на друга. Внутренние ссылки Markdown ведут на относительные `.md`-файлы.

Начни со статуса `draft`. Он означает, что статья ещё не прошла полную редакторскую приёмку. Для `verified` и `outdated` у первых четырёх типов обязательны область проверки `scope`, настоящая дата `verified_on` и непустой список публичных HTTPS-источников `sources`. У устаревшей статьи сохраняется историческая дата проверки. Изменение текста не является новым игровым тестом.

Перед `verified` другой читатель выполняет инструкцию без устных подсказок; у справочника сверяет значения и источники, у объяснения — логику и пример. Зелёная сборка, число заголовков или положительная оценка ИИ этого не заменяют.

### Сохранить исследование

Датированный опыт добавь в [дневник](reference/research-diary.md): сборка и дата, вопрос, входные данные и действия, наблюдение, вывод или гипотеза, ограничения и доступные доказательства. Ретроспективный пересказ помечай датой реконструкции. Если исходный журнал закрыт, сообщи об этом; статья должна содержать доступное объяснение или явно ограниченный вывод.

Исправленный технический вывод сопровождай датированной поправкой со ссылкой на прежнюю запись. Не подменяй прошлое наблюдение новым. Проверяй хеш скачиваемого файла по опубликованным байтам: окончания строк локальной копии могут отличаться.

Для пространственной механики показывай полное поле, обе армии, препятствия, размеры существ и оси X/Y. Строй повторяющиеся сетки из данных, отделяй измеренные клетки от предположительных. Пример связывает входные данные, промежуточные решения и проверенный результат; итоговый скриншот сам по себе не объясняет причину. Код обозначай как исходник, реконструкцию или псевдокод.

### Собрать сайт локально

Нужны Git, Python 3.10+ и Node.js 22+. Клонируй [репозиторий базы](https://github.com/Xaaalera/heroes5-knowledge), открой терминал в его каталоге и создай окружение:

```text
python -m venv .venv
```

Активируй его: в Windows PowerShell — `.venv\Scripts\Activate.ps1`, в Linux/macOS — `source .venv/bin/activate`. Затем:

```text
python -m pip install -r requirements.txt
npm ci
npm run build
npm run check
npx playwright install chromium
npm test
python -m mkdocs serve --watch-theme
```

Последняя команда запускает локальный просмотр и остаётся работающей; адрес показывается в терминале, Ctrl+C останавливает сервер. После правки SCSS выполни `npm run styles` во втором терминале. MkDocs следит за статьями и темой. Браузерные тесты используют отдельный сервер на порту 8769.

В Linux для Chromium также нужны системные зависимости: вместо команды установки браузера используй `npx playwright install --with-deps chromium`. Установка пакетов ОС может потребовать прав администратора; подробности — в [документации Playwright](https://playwright.dev/docs/browsers).

`npm run check` проверяет метаданные, переводы, ссылки, схемы и границы публичных данных; сообщает число черновиков отдельно. Браузерные тесты проверяют навигацию, поиск, языки и переполнение на пяти ширинах. Изменение интерфейса дополнительно осмотри с клавиатурой и при недоступном поиске. Не добавляй трекеры, удалённые шрифты и сбор личных данных. Происхождение иллюстраций и лицензии сохраняются в NOTICE.

### Проверить и опубликовать изменение

Этот этап выполняют сопровождающие репозитория. Для предложения статьи достаточно PR через GitHub; автору не нужно создавать результаты ревью или аттестацию самостоятельно. Сопровождающий получает JSON от независимых рецензентов по линзам `.claude/review.config.json`, включая отчёт docs и пять критиков статей. `<results.json>` ниже — путь к этому полученному файлу, а не готовый файл из репозитория. Если отчёта нет, сначала организуй ревью; не заполняй оценки за рецензентов.

`npm ci` устанавливает Git pre-push gate. Перед push нужны независимые ревью точного diff по пяти линзам конфигурации: craft, architecture, tests, docs и security. Они дополняют пять критиков статей. `npm run review:info` показывает базу, хеш и список статей; после правок ревью должно соответствовать окончательным байтам.

Сначала закоммить изменения исходников и статей: gate проверяет коммиты и отклоняет незакоммиченные правки. Формат полученного JSON проверяет [адаптер ревью](https://github.com/Xaaalera/heroes5-knowledge/blob/main/scripts/review-check.mjs): верхние поля — имена пяти линз, у каждой настоящие `verdict` и `score`. Поле `docs.review` содержит автора отчёта, проверенные файлы, восемь критериев с доказательствами, замечания и `articleCritiques`. Полный контракт этих вложенных полей находится в [валидаторе отчётов](https://github.com/Xaaalera/heroes5-knowledge/blob/main/scripts/review-docs.mjs); [тестовые примеры](https://github.com/Xaaalera/heroes5-knowledge/blob/main/scripts/review-docs.test.mjs) показывают форму, но не являются настоящими результатами ревью.

Передай JSON настоящих результатов в `npm run review:attest -- <results.json>`, закоммить созданную аттестацию отдельно и выполни `npm run review:gate`. Одна оценка docs недостаточна: отчёт покрывает восемь критериев и все изменённые Markdown-файлы, включая индекс агентов `docs/llms.txt`. Для каждой изменённой статьи нужны пять независимых критиков и текущий хеш. Явная база `--base` не отменяет отдельную границу введения правила критиков; не меняй базы ради обхода проверки.

Публикация GitHub Pages выполняется workflow репозитория. Успешный локальный тест не означает, что новая статья уже на сайте: проверь результат workflow и опубликованные RU/EN страницы.

### Данные и оформление

`faction` выбирает фон и цвет из `docs/assets/worlds/`; названия фракций находятся в `mkdocs.yml`. Координаты схем расстановки хранятся в `docs/assets/placement/observations.json`; `npm run figures` генерирует SVG. Меняй данные или генератор, не отдельные клетки SVG. Скачиваемая реконструкция `placement_walkthrough.py` имеет собственные тесты и явно заданные предположения; её нельзя выдавать за полный алгоритм игры.

`docs/llms.txt` — указатель для агентов на исходники и доказательства. Страницы содержат ссылки на него и исходный Markdown в GitHub; это не обещает автоматического чтения каждым клиентом. Ветка main может опережать развёрнутый сайт: при проверке фиксируй ревизию. Кеши Python и байткод не входят в публикацию.
