# Расширить C++-плагин и восстановить тестовую установку

Эта инструкция для разработчика, у которого уже работает [первый C++-проект xkit](devkit.md). Она объясняет добавление экспортируемой функции и отдельный случай восстановления файлов справочника после неудачной установки. Игроку с готовым модом эти действия не нужны.

## Подключить зависимости самостоятельного клона

Если работаешь с отдельным репозиторием нашего справочника или предиктора, открой PowerShell в каталоге этого клона. В общей мастерской используй её `sync-subrepos`, этот ручной порядок там не нужен.

Сначала прочитай `.gitmodules` выбранной ветки. Ниже порядок для веток с обоими подмодулями `devkit` и `game-api`. Старая опубликованная ветка предиктора пока объявляет только `devkit`: для неё используй `git submodule update --init devkit`, затем правила закреплённой версии SDK. Не передавай Git имя отсутствующего подмодуля и не добавляй новую зависимость только ради этой инструкции.

```text
git submodule update --init devkit game-api
git -C devkit rev-parse HEAD:game-api
git -C game-api rev-parse HEAD
```

Последние две команды показывают ожидаемый SDK и фактический коммиты Game API. Они должны совпадать. При несовпадении выбери согласованные закреплённые версии после проверки; не обновляй зависимость до main автоматически.

Путь `devkit/game-api` должен ссылаться на корневой `game-api`. Если по этому пути уже есть файлы или ссылка, не заменяй их этим способом: сначала выясни происхождение. Только пустую папку, оставленную Git для неинициализированного подмодуля, можно удалить командой `Remove-Item -LiteralPath devkit/game-api`. Затем создай ссылку:

```powershell
New-Item -ItemType Junction -Path devkit/game-api -Target (Resolve-Path game-api).Path
```

Junction показывает ту же физическую копию библиотеки под вторым путём. Не выполняй вложенный `git submodule update --init` для Game API: он создаст отдельный checkout. Эта подготовка связывает исходники; она не доказывает совместимость модифицированного кода с HMR или готовность игрового выпуска.

## Добавить экспортируемую функцию

Экспорт — имя функции, доступной другому модулю DLL. Это не новая команда игровой консоли: вызывающий код должен знать её параметры, результат и calling convention. Эти соглашения составляют ABI; нарушение может привести к сбою даже при успешной сборке.

1. Добавь функцию в исходники проекта `plugins/имя-проекта`. Сохрани обязательные функции контракта xkit.
2. Создай в том же дереве исходников один файл `.def`, например `exports.def`. Несколько таких файлов на одну DLL отклоняются.
3. В секции `EXPORTS` перечисли нужные имена. Имена должны соответствовать функциям, которые действительно собираются. Для C++ учитывай декорацию имён; простое имя обычно задают через `extern "C"` либо сопоставляют с внутренним именем символа. Формат и способы найти символ описаны в [Microsoft EXPORTS](https://learn.microsoft.com/en-us/cpp/build/reference/exports?view=msvc-170).
4. Сохрани файлы при работающем `xkit start имя-проекта`. Дождись успешных сборки и применения. Добавление или изменение `.def` отслеживается; правка только списка экспортов повторно линкует кешированные объектные файлы.
5. Проверь новую функцию совместимым потребителем. Наличие имени в DLL не доказывает правильность её вызова. Новый экспорт сам по себе не добавляет обработчик консольной команды.
6. Останови сеанс через Ctrl+C и выполни `xkit release имя-проекта`. Выпуск использует тот же `.def`. Проверь экспорт в DLL из полученного пакета, например через `dumpbin /exports ПУТЬ_К_DLL` в терминале Visual Studio Build Tools.

`имя-проекта` и `ПУТЬ_К_DLL` — подстановки: используй имя своего проекта и путь его DLL из распакованного выпуска. Ошибка компилятора или линкера не означает применение правки. При HMR не оставляй указатели на функции выгруженной версии; порядок снятия callback и передачи состояния описан в [Game API](../reference/game-api.md).

Начальный загрузчик и графическая оболочка обновляются при следующем запуске процесса. Для изменений во время разработки используй поддерживаемый контракт ядра или отдельного плагина. Перемещение старой DLL в папку проекта не переводит её автоматически на HMR.

## Восстановить файлы адаптера справочника

Этот раздел относится к адаптеру разработки справочника, который временно устанавливает DLL и H5U в собственную тестовую игру. Перед записью xkit сохраняет прежние файлы и манифест `recovery.json`. Это не команда удаления произвольного мода из основной игры.

1. Если установка или очистка завершилась ошибкой, сохрани путь `recovery.json` из журнала SDK. Найти журнал помогает `xkit diagnostics`; ошибка восстановления также содержит путь манифеста.
2. Закрой собственную тестовую игру и убедись, что её процесс завершился. Не переноси тестовую копию или рабочую папку во время восстановления.
3. В терминале с той же настройкой рабочей папки выполни:

```text
xkit sdk recover-bank "ПУТЬ_К_МАНИФЕСТУ"
```

Замени подстановку полным путём сохранённого `recovery.json`. Не создавай манифест вручную и не подменяй его файлом другой рабочей папки.

Команда проверяет рабочую папку, допустимые назначения и хеши файлов. Если файлы изменились извне или сохранённая копия повреждена, восстановление отклоняется. Сохрани материалы и прочитай сообщение; не удаляй резервные копии, чтобы обойти отказ.

При успехе xkit восстанавливает прежние файлы, удаляет использованные резервные копии и манифест, затем сообщает об окончании восстановления. Файл блокировки, оставшийся после завершения процесса, сам по себе не означает активную операцию: блокировку освобождает ОС.
