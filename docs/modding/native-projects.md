# Архитектура и расширение C++-модов

Здесь закреплены обязательные границы наших модов и xkit. Далее — работа с самостоятельным клоном, экспортами DLL и восстановлением тестовых файлов. Для первых команд начни с [руководства xkit](devkit.md); игроку с готовым модом эти действия не нужны.

## Обязательный архитектурный контракт {#architecture-contract}

**Игровая логика и интерфейс принадлежат моду. Среда разработки подключает мод через адаптер и не определяет его поведение.** Контракт обязателен при создании, расширении и переносе модов. Он задаёт требования; сам по себе этот текст не подтверждает соответствие текущих сборок.

### Ответственность слоёв

| Слой | За что отвечает | Что ему не принадлежит |
|---|---|---|
| Игра | Мир, бои, существа, камера, родные игровые окна и правила движка | Инструменты разработки модов |
| [Game API](../reference/game-api.md) | Проверенные привязки к поддерживаемой игре, доступ к игровым типам и известным точкам перехвата | Алгоритм предиктора, содержание справочника, управление проектом |
| Общий игровой загрузчик/runtime | Подключение модов, доставка событий, безопасный вызов и остановка обработчиков, согласованный контракт состояния | Правила конкретного мода и его интерфейс |
| Адаптер конкретного мода | Перевод событий и данных runtime в вызовы мода; регистрация его обработчиков; передача состояния и очистки | Дублирование алгоритма ради SDK |
| Логика и интерфейс мода | Расчёт результата, игровые правила мода, его модели, карточки, подсказки и состояние | Команды supervisor, управление сборкой и детали HMR |
| Инструменты xkit | Проекты, сборка, наблюдение за файлами, команды разработчика, журналы и подготовка пакетов | Обязательная служба на компьютере игрока |

Runtime — код, который выполняется внутри игры. Адаптер — часть интеграции отдельного мода. Supervisor — процесс xkit, который наблюдает за исходниками и управляет обновлениями при разработке. Эти роли не требуют по отдельной DLL на каждую строку таблицы: физическая упаковка может различаться. Каждый мод при этом поставляется независимо; общие игровые зависимости перечислены в его пакете.

### Направление зависимостей

- Адаптер зависит от публичного контракта runtime и вызывает логику своего мода. Общий runtime вызывает зарегистрированные обработчики через этот контракт.
- Логика мода не импортирует адаптер, внутренние типы SDK, расположение буферов runtime или команды среды разработки. Данные, нужные алгоритму, имеют смысл в предметной области мода.
- Игровой интерфейс мода может использовать Game API и родные игровые объекты. Независимость от xkit не означает независимость от самой игры.
- Общий runtime не знает категории существ предиктора, формулы расстановки или варианты армий конкретного хранилища. Эти решения остаются в модах.
- Общая библиотека хранит переиспользуемые привязки и механизмы с явным назначением. Перенос кода в неё требует реального общего потребителя; имя «общее» само по себе не является причиной.

**Пример границы для предиктора.** Runtime сообщает о событии подготовки боя. Адаптер формирует допустимый вход и вызывает существующий расчёт предиктора. Предиктор возвращает позиции и данные своего интерфейса; адаптер связывает нужные операции с жизненным циклом runtime. Политика доступности сведений задаётся отдельно: исследовательский режим не разрешает скрытые количества, грейды и готовое разделение нейтралов в обычном прогнозе.

| Допустимо | Нарушение границы |
|---|---|
| Адаптер преобразует игровой callback во вход мода | Алгоритм получает внутренний контекст SDK и читает его буферы |
| Мод хранит выбранный справочный грейд; адаптер сохраняет его при обновлении | Выбранный грейд хранится только в Python-процессе разработчика |
| Runtime обеспечивает безопасный вызов очистки мода | Runtime содержит особую ветку для расстановки джиннов |
| Мод использует проверенные игровые привязки Game API | Мод ищет исходники или рабочую папку xkit во время игры |
| Новый адаптер вызывает прежний алгоритм и интерфейс | Для подключения к SDK создаётся упрощённая копия мода |

### Два режима работы

**Разработка через xkit:** исходники мода → сборка временной DLL → проверка совместимости → безопасная смена версии в тестовой игре. Инструменты разработчика и консоль помогают наблюдать результат. C++ продолжает компилироваться; HMR автоматизирует сборку и подключение.

**Готовый мод у игрока:** установленный пакет → обычный запуск Heroes/Lobby → игровой загрузчик/runtime → адаптер → та же логика мода. Отдельные процессы xkit, Python/Node, исходники, рабочая папка и консоль разработчика не требуются. Ресурсный мод поставляет собственный H5U, нативный — собственную DLL; необходимые общие игровые файлы явно описаны.

Разработка и выпуск используют одну реализацию поведения. Способ подключения и упаковки может отличаться. Условная компиляция не должна незаметно отключать функции в одном из режимов. Промежуточная DLL, пригодная для HMR, не становится готовым игровым пакетом от простого копирования.

### Состояние, обновление и очистка

- Мод определяет смысл своего состояния. Адаптер отвечает за передачу этого состояния через согласованный контракт; runtime — за срок жизни предоставленного хранилища. Типы транспорта не становятся моделью данных алгоритма.
- Перед заменой версии проверяются совместимость контракта и формата состояния. Если совместимость не доказана, обновление отклоняется с понятной причиной. Нельзя молча сбрасывать состояние или менять его смысл.
- Нельзя выгружать DLL, пока игра или другой обработчик может вызвать принадлежащую ей функцию. Обработчики снимаются через согласованный механизм; игровые объекты и ссылки освобождаются в допустимом потоке игры.
- Отказ обновления должен сохранять прежнюю рабочую версию, когда состояние позволяет это подтвердить. Это не обещание отката любых уже совершённых действий игры.
- Изменения загрузчика, несовместимого состояния или ресурсов могут потребовать перезапуска. Причина фиксируется отдельно; окончание проверки или ответа не является причиной закрывать тестовую игру.

### Когда перенос считается завершённым

| Условие | Требуемое доказательство |
|---|---|
| Соблюдены границы исходников | Архитектурное ревью зависимостей и владения поведением; нарушения блокируют приёмку |
| Сохранены прежние функции | Перечень функций до переноса и результаты проверки каждой после переноса, включая интерфейс и очистку |
| Корректен готовый пакет | Проверка именно выпущенных файлов, точек входа DLL, зависимостей и установочных путей |
| Разработка поддерживает заявленный HMR | Проверки смены кода, состояния, обработчиков и отказов в одной подтверждённой сессии |
| Игроку не нужна среда разработки | Обычный запуск итогового пакета без процессов разработчика, исходников и путей мастерской; проверка поведения мода |
| Моды независимы | Проверка каждого пакета отдельно и совместной установки; загрузка/отключение по требованию проверяются дополнительно, если заявлены |

Успешная сборка, наличие мода в списке, статическая проверка DLL и работа внутри SDK подтверждают разные свойства. Ни одно из них отдельно не доказывает завершение переноса. Для предиктора прежние серии точности также не переносятся на новую сборку: нужны результаты именно её расчёта.

### Контроль изменений и текущие ограничения

AGENTS корня, девкита и обоих модов ссылаются на этот контракт. Архитектурное ревью обязано проверять направление зависимостей, отсутствие утечки реализации SDK и сохранность поведения. При изменении решения обновляются контракт и связанные критерии приёмки с объяснением причины; обход правил под видом локальной правки недопустим.

В разрабатываемом нативном сборщике уже обязательна [статическая проверка игрового ZIP](#player-package-check). Она не доказывает отсутствие программно загружаемых зависимостей и не проверяет разделение исходников. Автоматическая проверка всех зависимостей между слоями пока не реализована; за неё отвечает архитектурное ревью. Разные пути упаковки, включая справочник, требуют своих проверок. Полная сохранность функций перенесённого предиктора и обычный запуск его новой управляемой сборки ещё не подтверждены.

## Подключить зависимости самостоятельного клона

Если работаешь с отдельным репозиторием нашего справочника или предиктора, открой PowerShell в каталоге этого клона. В общей мастерской используй её `sync-subrepos`, этот ручной порядок там не нужен.

Сначала прочитай `.gitmodules` выбранной ветки. Ниже порядок для веток с обоими подмодулями `devkit` и `game-api`. Старая опубликованная ветка предиктора пока объявляет только `devkit`: для неё используй `git submodule update --init devkit`, затем правила закреплённой версии SDK. Не передавай Git имя отсутствующего подмодуля и не добавляй новую зависимость только ради этой инструкции.

```text
git submodule update --init devkit game-api
git -C devkit rev-parse HEAD:game-api
git -C game-api rev-parse HEAD
```

Последние две команды показывают ожидаемый SDK и фактический коммиты Game API. Они должны совпадать. При несовпадении выбери согласованные закреплённые версии после проверки; не обновляй зависимость до main автоматически.

Путь `devkit/game-api` должен ссылаться на корневой `game-api`. Если по этому пути уже есть файлы или ссылка, не заменяй их этим способом: сначала выясни происхождение. Только пустую папку, оставленную Git для неинициализированного подмодуля, можно удалить командой `Remove-Item -LiteralPath devkit/game-api`. Затем создай ссылку:

```powershell
New-Item -ItemType Junction -Path devkit/game-api -Target (Resolve-Path game-api).Path
```

Junction показывает ту же физическую копию библиотеки под вторым путём. Не выполняй вложенный `git submodule update --init` для Game API: он создаст отдельный checkout. Эта подготовка связывает исходники; она не доказывает совместимость модифицированного кода с HMR или готовность игрового выпуска.

## Добавить экспортируемую функцию

Экспорт — имя функции, доступной другому модулю DLL. Это не новая команда игровой консоли: вызывающий код должен знать её параметры, результат и calling convention. Эти соглашения составляют ABI; нарушение может привести к сбою даже при успешной сборке.

1. Добавь функцию в исходники проекта `plugins/имя-проекта`. Сохрани обязательные функции контракта xkit.
2. Создай в том же дереве исходников один файл `.def`, например `exports.def`. Несколько таких файлов на одну DLL отклоняются.
3. В секции `EXPORTS` перечисли нужные имена. Имена должны соответствовать функциям, которые действительно собираются. Для C++ учитывай декорацию имён; простое имя обычно задают через `extern "C"` либо сопоставляют с внутренним именем символа. Формат и способы найти символ описаны в [Microsoft EXPORTS](https://learn.microsoft.com/en-us/cpp/build/reference/exports?view=msvc-170).
4. Сохрани файлы при работающем `xkit start имя-проекта`. Дождись успешных сборки и применения. Добавление или изменение `.def` отслеживается; правка только списка экспортов повторно линкует кешированные объектные файлы.
5. Проверь новую функцию совместимым потребителем. Наличие имени в DLL не доказывает правильность её вызова. Новый экспорт сам по себе не добавляет обработчик консольной команды.
6. Останови сеанс через Ctrl+C и выполни `xkit release имя-проекта`. Выпуск использует тот же `.def`. Проверь экспорт в DLL из полученного пакета, например через `dumpbin /exports ПУТЬ_К_DLL` в терминале Visual Studio Build Tools.

`имя-проекта` и `ПУТЬ_К_DLL` — подстановки: используй имя своего проекта и путь его DLL из распакованного выпуска. Ошибка компилятора или линкера не означает применение правки. При HMR не оставляй указатели на функции выгруженной версии; порядок снятия callback и передачи состояния описан в [Game API](../reference/game-api.md).

Начальный загрузчик и графическая оболочка обновляются при следующем запуске процесса. Для изменений во время разработки используй поддерживаемый контракт ядра или отдельного плагина. Перемещение старой DLL в папку проекта не переводит её автоматически на HMR.

<span id="player-package-check"></span>

**Проверка готовой DLL при выпуске.**

В разрабатываемой версии сборщика перед выдачей игрового ZIP автоматически проверяются формат DLL, точка входа, которую вызывает загрузчик, и обычные/отложенные зависимости. Ошибка о недостающей точке входа может означать, что вместо готового мода передана промежуточная DLL для разработки. Ошибка о необъявленной зависимости требует проверить сборку и состав пакета; установка SDK на компьютер игрока не является исправлением.

Эта проверка ещё не опубликована. Она не запускает игру и не обнаруживает все зависимости, загружаемые программно. Обычный запуск итогового пакета через Heroes/Lobby без процессов разработки и проверка сохранности функций остаются отдельными условиями готовности.

## Восстановить файлы адаптера справочника

Этот раздел относится к адаптеру разработки справочника, который временно устанавливает DLL и H5U в собственную тестовую игру. Перед записью xkit сохраняет прежние файлы и манифест `recovery.json`. Это не команда удаления произвольного мода из основной игры.

1. Если установка или очистка завершилась ошибкой, сохрани путь `recovery.json` из журнала SDK. Найти журнал помогает `xkit diagnostics`; ошибка восстановления также содержит путь манифеста.
2. Закрой собственную тестовую игру и убедись, что её процесс завершился. Не переноси тестовую копию или рабочую папку во время восстановления.
3. В терминале с той же настройкой рабочей папки выполни:

```text
xkit sdk recover-bank "ПУТЬ_К_МАНИФЕСТУ"
```

Замени подстановку полным путём сохранённого `recovery.json`. Не создавай манифест вручную и не подменяй его файлом другой рабочей папки.

Команда проверяет рабочую папку, допустимые назначения и хеши файлов. Если файлы изменились извне или сохранённая копия повреждена, восстановление отклоняется. Сохрани материалы и прочитай сообщение; не удаляй резервные копии, чтобы обойти отказ.

При успехе xkit восстанавливает прежние файлы, удаляет использованные резервные копии и манифест, затем сообщает об окончании восстановления. Файл блокировки, оставшийся после завершения процесса, сам по себе не означает активную операцию: блокировку освобождает ОС.
