# Game API для C++-плагинов

Game API — общая C++-библиотека наших модов и xkit. Она хранит проверки поддерживаемой сборки и известные точки подключения к игре. Используй её вместо копирования привязок из другого плагина. Для первого проекта начни с [руководства xkit](../modding/devkit.md).

## Подключить библиотеку

Нужны Windows 10/11, MSVC с целевой архитектурой x86, C++20 и CMake 3.21+. Сама игра и её DLL остаются 32-битными. Библиотека поддерживает [исследованную сборку Universe](universe-build.md); совпадения названия EXE недостаточно.

Размести исходники [Game API](https://github.com/Xaaalera/heroes5-game-api) в зависимости `game-api` своего CMake-проекта. В проектах мастерской используй уже подключённую каноническую зависимость. Затем добавь после объявления своей цели `my_plugin`:

```cmake
add_subdirectory(game-api)
target_link_libraries(my_plugin PRIVATE heroes5_game_api)
```

Это библиотека заголовков: отдельной Game API DLL нет. Цель CMake подключает каталог `include`, C++20 и Windows-библиотеку `bcrypt` для проверки хешей. Эти строки не устанавливают игровые хуки и не делают старый плагин совместимым с HMR.

## Что можно переиспользовать

| Заголовок | Назначение | Обязанность вызывающего кода |
|---|---|---|
| `h5/build.hpp` | `VerifyGame`: проверить имена и SHA-256 бинарников поддерживаемой установки | Проверять до использования привязок; не продолжать после отказа |
| `h5/process.hpp` | `OpenOwnedProcess`: открыть конкретный процесс своего запуска и проверить время создания, путь и сборку | Передать сведения своего запуска; закрыть успешный handle через `CloseHandle` |
| `h5/hooks.hpp` | Именованные точки выбора армии хранилища, показа расстановки, начала атаки, наведения, скриптов и выхода | Проверить сигнатуру и контракт вызова; каталог не устанавливает hook |
| `h5/actor_input.hpp` *(локальная исследовательская версия; ещё не опубликована)* | Записи входных параметров армий и отдельные наблюдатели фактического результата; `ReadCombatRosterCount` читает полный размер списка юнитов | Читать только в соответствующем живом callback; скрытые входы требуют явного исследовательского режима, результаты после Start используются только для сверки |
| `h5/console.hpp` | `DispatchConsoleCommand` и `DispatchGameText`: передать штатную команду, событие или скрипт карты | Вызывать на потоке окна своей игры; отдельно проверить результат действия |
| `h5/script_observers.hpp` | Общие подписки на вызов игрового диспетчера скриптов | Удалить свой callback до выгрузки или замены DLL |
| `h5/camera_input.hpp` | Подписки для подавления ввода камеры над панелью | Менять подписки на проверенном игровом потоке; не блокировать управление над картой |
| `h5/adventure_input.hpp` | Изоляция подтверждённых нажатий клавиш при фокусе консоли | Сохранять исходную обработку при скрытой консоли; это не перехват всех видов ввода |
| `h5/graphics_lifetime.hpp` | Исправление времени жизни графической обёртки в памяти процесса | Только при запуске до инициализации графики, с остановленными потоками собственного процесса; при отказе не продолжать запуск |
| `h5/image_placement.hpp` | Проверка файла и размещения загруженной DLL без изменения памяти | Остановить свой загрузчик на событии загрузки DLL и сохранить handle исходного файла |

`OpenOwnedProcess` не ищет игру автоматически и не разрешает подключение к чужому процессу. При отказе функция закрывает открытый handle сама. Проверки сборки не меняют файлы игры.

## Передать событие или скрипт

`DispatchGameText` принимает существующий `ConsoleCommandRequest` и тип запроса:

| Тип | Допустимый текст |
|---|---|
| 1: именованное событие | ASCII-буквы, цифры и подчёркивание; до 127 символов |
| 2: скрипт карты | Печатные ASCII-символы; до 4095 символов |

Тип 0 относится к отдельной `DispatchConsoleCommand`, которая принимает широкую строку. Пустой текст, неверные размер или версия запроса, неизвестный тип и вызов с другого потока отклоняются. Игровая строка создаётся и освобождается средствами игры на её потоке окна.

Успешная передача не доказывает выполнение игрового действия. После снимка проверь новый файл; после изменения армии — прочитай её состояние. Для готовых действий используй [команды xkit](xkit-commands.md), не собирай скрипт вручную без необходимости.

## Подписаться и безопасно обновить DLL

Диспетчер скриптов поддерживает до 64 подписчиков. `FindScriptObservers` проверяет известный контракт общего диспетчера, а `AddScriptObserver` и `RemoveScriptObserver` добавляют и снимают отдельный callback. Создание общего обработчика и публикация перехвата требуют проверки исходной сигнатуры; создание хранилища само по себе перехват не устанавливает.

Регистрация, удаление и вызов идут на одном проверенном игровом потоке. Callback имеет контракт `cdecl void()`: возвращается обычным способом, не вызывает повторно тот же runtime и не сохраняет указатели на временные данные или состояние плагина.

При обновлении плагина:

1. Прекрати новые вызовы и дождись завершения текущих.
2. Подтверди удаление всех callback старой DLL.
3. Передай предусмотренное контрактом состояние.
4. Загрузи новую DLL, восстанови состояние и зарегистрируй новые callback.

Общий обработчик остаётся в процессе до выхода игры; при отсутствии подписчиков вызывает исходную функцию. Отключение одного плагина не должно снимать подписки других. Это доверенный контракт внутри процесса, а не защита от другого кода, уже способного менять память игры.

## Графическая цепочка: только загрузчик

`VerifyGraphicsFiles` по умолчанию принимает исходную графическую библиотеку Universe. Для цепочки SDK вызывающий код явно передаёт доверенный SHA-256 оболочки из своей проверенной сборки; исходная библиотека должна оставаться неизменённой в `d3d9.universe.dll`. Сторонний файл с хешем в папке игры не делает оболочку доверенной.

`VerifyOwnedImagePlacement` проверяет файл и отображение DLL до её использования. Загрузчик сохраняет handle файла из события загрузки: проверяется именно этот открытый файл, а не заново открытый путь. Функция не продолжает событие загрузки, не передаёт владение handle и не меняет память процесса.

`RepairOwnedGraphicsProxyLifetime` меняет исполняемую память процесса, чтобы обёртка устройства сохранялась при оставшихся ссылках. При нуле ссылок сохраняется исходное освобождение. Файлы игры не меняются. Это исправление только для поддерживаемой сборки, до инициализации графики и при остановленных потоках собственного процесса; оно не предназначено для HMR или работающей карты.

После записи и отката проверяются байты, защита страницы и принадлежность образу. При отказе запуск продолжать нельзя, в том числе после попытки отката. Внутренний маршрут оболочки SDK также ограничен первой инициализацией проверенной оригинальной DLL, до создания графических объектов и передачи фабрики игре. Проверки логики транзакции с подменёнными операциями памяти не заменяют живую проверку загрузчика.

## Границы проверки

Для нативных тестов открой терминал в отдельном checkout Game API с настроенным MSVC и выполни:

```text
cmake -S . -B .local/build -A Win32
cmake --build .local/build --config Release
ctest --test-dir .local/build -C Release --output-on-failure
```

Команды собирают тест библиотеки, а не запускают игру. Если генератор CMake не поддерживает `-A Win32`, выбери установленный Visual Studio generator. Не смешивай x64 и x86 в одной папке сборки. Структура рабочего репозитория проверяется отдельно: `python -X utf8 scripts/docs-check.py --structure-only`; этот режим не проверяет соответствие изменений кода статье.

Именованные точки перенесены из существующих модов и SDK. Их наличие в каталоге не означает новую живую проверку каждого hook. Поток, calling convention, сохранение регистров и время жизни callback остаются частью контракта потребителя.

Нативные проверки библиотеки покрывают хеши, отказы неверной сборки и процесса, общие подписки, сохранение состояния вычислений и отдельные проверки графики и ввода. Сохранённые живые опыты SDK проверяли двух подписчиков, обновление ядра и плагинов, откат и независимое отключение. Эти результаты относятся к конкретным исходникам и сценариям; они не подтверждают все карты, весь ввод или сетевую игру.

При добавлении привязки сначала подтверди сигнатуру, контракт вызова, поток и время жизни, затем сохрани воспроизводимый тест и границы проверки. Непроверенную гипотезу отмечай как гипотезу. Численные привязки находятся в [исходниках библиотеки](https://github.com/Xaaalera/heroes5-game-api/tree/main/include/h5); человеческое описание использует имена и назначение.
